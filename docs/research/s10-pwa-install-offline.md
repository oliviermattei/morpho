## Target story

**s10-pwa-install-offline — Installation et lecture hors ligne**
*As a* utilisateur *I want* installer morpho sur mon écran d'accueil et l'ouvrir sans réseau *so that* mes données ne soient jamais purgées et que l'app s'ouvre toujours.
Complexity : 3. Dépendances : **toutes les stories précédentes** (s01 → s09).

### Critères d'acceptation (verbatim, `docs/stories.md`)

- [ ] L'app expose un manifest valide (nom, icônes aux tailles requises, `display: standalone`, couleur de thème) et s'installe sur l'écran d'accueil iOS.
- [ ] Lancée depuis l'écran d'accueil, l'app s'ouvre en mode standalone, sans barre d'adresse du navigateur.
- [ ] Un service worker met en cache le shell applicatif : ouverte sans réseau, l'app affiche son interface et le dernier état connu, jamais la page d'erreur du navigateur.
- [ ] Hors ligne, l'app signale clairement qu'elle affiche des données potentiellement périmées.
- [ ] Hors ligne, une tentative de saisie est refusée par un message explicite ; rien n'est mis en file d'attente et aucune donnée n'est perdue silencieusement.
- [ ] **Avant merge** : sur un déploiement de preview installé sur l'appareil, deux déploiements successifs sont effectués ; après le second, un lancement à froid depuis l'écran d'accueil sert la nouvelle version sans vidage manuel du cache. Le protocole et les identifiants de déploiement sont consignés dans la review.
- [ ] La stratégie de cache exclut les réponses de l'API contenant les données d'un utilisateur d'un cache partagé ou persistant après déconnexion : se déconnecter puis rouvrir hors ligne n'expose aucune donnée de la session précédente.

Post-ship (confirmation, hors gate) : rejouer le même lancement à froid sur l'URL de production après le premier déploiement réel.

**Pas d'écran** au sens `/ks-design` : la story ne crée pas de nouvelle page produit. Elle ajoute cependant **deux éléments visibles** (bandeau « données potentiellement périmées », refus de saisie hors ligne) que `docs/design-system.md` a déjà attribués : `alert` pour le bandeau, `sonner` pour le message. Elle doit aussi combler le **gap n°3 du design system** (« Icônes et écran de démarrage PWA — tailles, masque iOS, couleur de thème du manifest. À traiter en s10 »).

```js
                  crossOrigin={!manifestOrigin && process.env.VERCEL_ENV === 'preview' ? 'use-credentials' : undefined} />);
}
```

Deux faits utiles : (a) le lien n'est émis que si `metadata.manifest` est résolu — et `resolve-metadata.js` le remplit automatiquement depuis le fichier `app/manifest.ts` ; (b) **Next gère déjà le cas des previews Vercel protégées** en mettant `crossOrigin="use-credentials"`.

**iOS / standalone** (`dist/esm/lib/metadata/metadata.js`, bloc `// --- Apple Web App ---`) :

L'échappatoire, si le tag legacy s'avère nécessaire, est `metadata.other` (`generate-metadata.md` § `other` : `other: { custom: 'meta' }` → `<meta name="custom" content="meta" />`, valeur tableau acceptée pour les clés répétées).

## Traps & constraints

### 1. La story dépend de neuf stories qui n'existent pas encore

`docs/stories.md` place s10 en dernier délibérément (« mettre en cache un shell qui change encore à chaque story ferait payer le coût du versioning de cache à chaque livraison »). Aujourd'hui le dépôt est au boilerplate `create-next-app`. Tout ce qui suit sur « le shell », « les données du dernier état connu » ou « la déconnexion » suppose s01→s09 livrées. **Cette recherche devra être relue au moment du `/ks-plan`** : le code réel aura changé, en particulier `src/proxy.ts`, `src/lib/auth.ts` et le formulaire de saisie.

### 2. `defaultCache` viole frontalement le dernier critère d'acceptation

Repris tel quel de l'exemple amont, `defaultCache` met en cache **persistant** :

- `GET /api/*` (hors `/api/auth/*`) dans un cache nommé `"apis"`, `NetworkFirst`, `maxAgeSeconds: 86400` ;
- le HTML des pages same-origin dans `"pages"` ;
- les payloads RSC (`RSC: 1`) dans `"pages-rsc"` et `"pages-rsc-prefetch"` ;
- le reste same-origin dans `"others"`.

Or `docs/architecture.md` impose que **toute donnée transite par un Server Component ou un route handler** : le HTML et les payloads RSC de morpho *contiennent* les mensurations de l'utilisateur. Utiliser `defaultCache` sans le retailler fait échouer le critère 7 par construction — et la démonstration est triviale : se déconnecter, couper le réseau, rouvrir, le cache `"pages"` resservira la silhouette du compte précédent.

Deux leviers, tous deux nécessaires :
1. un `runtimeCaching` **écrit à la main** plutôt que `defaultCache` (les stratégies et plugins sont exportés par `serwist`), qui distingue le shell statique (`/_next/static/**`, icônes) des réponses porteuses de données ;
2. une **purge explicite à la déconnexion** — `caches.keys()` + `caches.delete()` sur les caches applicatifs, déclenchée dans le flux `signOut` de s02, plus `cacheOnNavigation={false}` sur `SerwistProvider` (sinon chaque navigation réinjecte l'URL visitée dans le cache runtime, voir n°3).

**Tension réelle à arbitrer au plan, pas à masquer** : le critère 3 demande « l'interface **et le dernier état connu** » hors ligne, le critère 7 interdit de garder ces mêmes données en cache après déconnexion. Les deux ne sont conciliables que si les données mises en cache sont **purgées à la déconnexion**, pas si elles ne sont jamais mises en cache. Un choix « on ne cache aucune donnée » satisferait 7 et ferait échouer 3 ; un choix « on cache tout » fait l'inverse. Le point d'équilibre est : cacher, mais lier explicitement le cycle de vie du cache à celui de la session.

### 3. `SerwistProvider` a trois défauts silencieux qui jouent contre la story

Lu dans `src/index.react.tsx` :

- `cacheOnNavigation = true` → patch de `history.pushState`/`replaceState` + listener `online` qui envoient `CACHE_URLS` au SW pour **chaque URL visitée**. Sur une app entièrement authentifiée, c'est un mécanisme de mise en cache de données utilisateur activé par défaut.
- `reloadOnOnline = true` → `location.reload()` au retour du réseau. Si l'utilisateur est en train de remplir le formulaire de saisie (s03/s05) quand le wifi revient, **la page est rechargée et la saisie perdue**. Le critère 5 dit « aucune donnée perdue silencieusement » : c'est exactement le scénario qu'il vise.
- `options.type` par défaut `"module"` et `options.scope` par défaut `"/"` : le scope `/` n'est légal que parce que le route handler renvoie `Service-Worker-Allowed: "/"` (voir n°5).

### 4. `src/app/sw.ts` et `npm run typecheck` — vérifié empiriquement

`ServiceWorkerGlobalScope` **n'existe pas** dans `lib.dom.d.ts` (0 occurrence) et n'existe que dans `lib.webworker.d.ts` (2 occurrences), vérifié dans `morpho/node_modules/typescript/lib/`. Or `tsconfig.json` inclut `**/*.ts` : `src/app/sw.ts` sera typechecké avec `lib: ["dom","dom.iterable","esnext"]` et échouera.

Deux options, testées toutes les deux avec le `tsc` 5.9.3 du projet :

| Option | Résultat mesuré |
|---|---|
| Ajouter `"webworker"` au `lib` global (ce que fait l'exemple amont) | **sans** `skipLibCheck` : mur d'erreurs `TS6200` / `TS2374` / `TS2403` / `TS2717` (conflits `dom` ↔ `webworker` sur `self`, `location`, `navigator`, `FormData`, `URL`, `Notification`…). **Avec** `skipLibCheck: true` — ce que morpho a déjà — `exit 0`, aucune erreur. Ça passe, mais au prix d'ambiguïtés silencieuses sur les globals partagés dans **tout** le projet. |
| `/// <reference lib="webworker" />` en tête de `sw.ts`, `lib` global inchangé | `exit 0`, aucune erreur, portée limitée au seul fichier. Testé avec `declare const self: ServiceWorkerGlobalScope; self.addEventListener("install", …)` et `navigator.onLine`. |

La seconde option est la seule qui n'élargisse pas le `lib` de l'app entière. À trancher au plan, mais le fait est établi : **copier le `tsconfig.json` de l'exemple amont n'est pas neutre**.

Note connexe : `vitest.config.ts` a `include: ["src/**/*.test.{ts,tsx}"]` et `environment: "jsdom"`. Le service worker lui-même **n'est pas testable en Vitest** (pas de `ServiceWorkerGlobalScope`, pas de `CacheStorage` réelle dans jsdom). Ce qui reste testable en unitaire : la logique de détection hors ligne, le composant bandeau, la fonction de purge des caches (avec un `caches` mocké), le contenu du manifest s'il est extrait dans une fonction pure.

### 5. Le service worker est servi depuis `/serwist/sw.js`, pas depuis la racine

Par défaut, un SW servi depuis `/serwist/sw.js` ne peut contrôler que `/serwist/**`. Le montage ne fonctionne que grâce à l'en-tête `Service-Worker-Allowed: "/"` posé par le `GET` généré, combiné au `scope: "/"` de `SerwistProvider`. **Si cet en-tête est perdu**, l'enregistrement échoue avec une `SecurityError` et le hors-ligne ne fonctionne jamais. Points de perte possibles :

- le handler est prérendu (`dynamic = "force-static"`, `revalidate = false`) : les en-têtes doivent survivre à la mise en cache statique de Vercel — **non vérifiable ici** (voir Questions ouvertes) ;
- une règle `headers()` ajoutée dans `next.config.ts` sur `/serwist/:path*` **ne** supprime pas les en-têtes du handler (elle en ajoute), mais une règle avec la même clé écrase : « If two headers match the same path and set the same header key, the last header key will override the first ».

Corollaire d'intégration : `src/proxy.ts` (s02) doit laisser passer `/serwist/:path*` **sans session**. Le proxy Neon Auth ne connaît qu'une sanction, `redirect_login` (constaté dans `docs/research/s02-connect-magic-link.md`) : une redirection HTML sur `/serwist/sw.js` produit un script invalide et un échec d'enregistrement silencieux. Idem pour `/manifest.webmanifest`, les icônes et `/~offline`.

### 6. Le SW est un module ES — enregistrement `type: "module"`

`build.ts` force `format: "esm"` et `bundle: true` ; `SerwistProvider` enregistre avec `type: options?.type || "module"`. Les service workers en module ES sont un support **récent** dans Safari. La cible de morpho est explicitement « iOS Safari en mode standalone, portrait, 375 px » (`docs/architecture.md` § Design/UX). Si l'iPhone de test ne le supporte pas, le SW ne s'enregistre pas du tout — et le symptôme est un hors-ligne qui « ne marche pas », sans erreur parlante.

Le repli existe et est entièrement dans les options exposées : `esbuildOptions: { format: "iife" }` côté route + `options={{ type: "classic" }}` côté provider. À constater sur l'appareil, pas à supposer.

### 7. Le `revision` de l'exemple amont est cassé sur Vercel

```ts
const revision = spawnSync("git", ["rev-parse", "HEAD"], { encoding: "utf-8" }).stdout.trim() ?? crypto.randomUUID();
```

Deux problèmes cumulés : (a) le conteneur de build Vercel n'expose pas forcément un dépôt `.git` exploitable ; (b) `??` est le coalescing **nullish** — si `git` échoue, `stdout` vaut `""`, `"".trim()` vaut `""`, et `"" ?? x` vaut `""`, **pas** l'UUID. Le `revision` de `/~offline` deviendrait la chaîne vide, figée d'un déploiement à l'autre : la page de repli précachée ne serait jamais rafraîchie. C'est exactement le « bug fantôme » que le critère 6 cherche à prévenir.

La source fiable est `process.env.VERCEL_GIT_COMMIT_SHA`, que Next utilise lui-même (`dist/trace/trace-uploader.js`), avec un repli explicite en `||` (pas `??`).

### 8. Ce que le précache couvre — et ne couvre pas

`generateGlobPatterns` (`src/lib/utils.ts`) produit exactement :

```
<distDir>static/**/*.{js,css,html,ico,apng,png,avif,jpg,jpeg,jfif,pjpeg,pjp,gif,svg,webp,json,webmanifest}
public/**/*
```

Donc : les chunks JS/CSS et les assets de `public/` sont précachés, **aucune page HTML ne l'est**. Le « shell applicatif » du critère 3 ne vient donc pas du précache : il vient soit du cache runtime (`NetworkFirst` sur le HTML, qui exige une visite en ligne préalable), soit du `fallbacks` (`/~offline`). Un premier lancement hors ligne après installation, sans visite en ligne préalable de la route, tombera sur le repli. À expliciter dans le plan et dans le protocole de review — sinon le critère sera « vérifié » sur un cas favorable.

Deuxième conséquence : `public/**/*` précache **tout** `public/`, y compris les `next.svg`, `vercel.svg`, `globe.svg`, `window.svg`, `file.svg` du boilerplate encore présents aujourd'hui. Ils doivent avoir disparu (s01 les retire déjà pour le critère anti-analytics de sa propre story), sinon on précache des logos Vercel dans une app dont le PRD interdit les traceurs tiers.

### 9. `theme_color` / `themeColor` contre la règle « aucune couleur en dur »

`docs/design-system.md` : « Aucune couleur en dur dans un composant — les valeurs viennent des tokens », et les tokens sont en **OKLCH** (`oklch(1 0 0)`, `oklch(0.145 0 0)`…). Mais `manifest.theme_color`, `manifest.background_color` et `viewport.themeColor` sont des **chaînes littérales** dans un fichier JSON/JS : elles ne peuvent pas référencer une variable CSS, et la prise en charge d'`oklch()` par le parseur de manifest d'iOS n'est pas acquise.

C'est un **design system gap** au sens des règles du dépôt (`AGENTS.md` : « A need the system doesn't cover = a "design system gap" to report, never to fill freestyle »), pas une licence à inventer un hexadécimal. Le gap n°3 de `docs/design-system.md` (« Icônes et écran de démarrage PWA — tailles, masque iOS, couleur de thème du manifest. À traiter en s10 ») le prévoit déjà : la valeur doit être **décidée et inscrite dans le design system**, pas choisie dans le code du manifest.

Note complémentaire : le design system impose que l'app suive `prefers-color-scheme`. `viewport.themeColor` accepte un tableau `{ media, color }` (vérifié dans `generate-viewport.md`), donc le double thème est exprimable. `manifest.theme_color`, lui, est une valeur unique.

### 10. `cacheComponents` est un interrupteur qui casserait la route Serwist

`createSerwistRoute` **exporte** `dynamic`, `dynamicParams` et `revalidate`. Le doc Next : ces trois options sont « removed when Cache Components is enabled » (v16.0.0). Le commentaire en tête de `src/index.ts` amont le dit aussi : « This version is for when **NOT** using `cacheComponents`. » `next.config.ts` ne l'active pas aujourd'hui — c'est une contrainte à protéger, pas un acquis.

### 11. Interaction non évaluée entre `deploymentId` et le précache

`deploymentId` ajoute `?dpl=<id>` aux URLs d'assets statiques. Le manifeste de précache est construit par **glob sur les fichiers** de `.next/static/**` et `public/**`, puis réécrit par `manifestTransforms` (`src/lib/validate.ts`) en `<assetPrefix>/_next/…` et `<basePath>/…` — **sans** query. Activer `deploymentId` pour « aider » la mise à jour risquerait donc de désaligner les URLs précachées et les URLs réellement demandées. Ne pas l'activer sans mesure.

### 12. Le critère 6 (deux déploiements de preview) n'est pas exécutable dans cet environnement

Il exige : un projet Vercel configuré, deux déploiements de preview successifs, un iPhone réel, une installation sur l'écran d'accueil, un lancement à froid. Aucune de ces conditions n'est disponible ici (ni Vercel CLI, ni credentials — voir *blockers*). C'est une vérification **manuelle et humaine**, et le critère demande explicitement que « le protocole et les identifiants de déploiement soient consignés dans la review ». Le plan doit produire ce protocole comme un livrable écrit, pas comme une case à cocher.

Sous-piège identifié : les déploiements de preview Vercel sont protégés par Vercel Authentication. Next gère le manifest (`crossOrigin="use-credentials"` quand `VERCEL_ENV === 'preview'`), mais le comportement de l'enregistrement du service worker et du partage de cookies entre Safari et une app installée sur l'écran d'accueil n'a **pas** pu être établi ici (voir Questions ouvertes).

### 13. Environnement de dev : `defaultCache` est neutralisé, le hors-ligne ne se teste pas en `next dev`

`src/index.worker.ts` : en `NODE_ENV !== "production"`, `defaultCache` est réduit à `[{ matcher: /.*/i, handler: new NetworkOnly() }]`. De plus, `validateInjectManifestOptions` force `disablePrecacheManifest: DEV` et `additionalPrecacheEntries: []` en dev. **Rien du comportement hors ligne ne se reproduit sous `npm run dev`** — c'est précisément ce que `docs/stories.md` appelle « un bug fantôme sur mobile, très coûteux à diagnostiquer parce qu'il ne se reproduit pas en dev ». La vérification passe par `npm run build && npm run start`, ou par une preview.

Conséquence Playwright : `playwright.config.ts` démarre `npm run dev` par défaut. Un e2e qui prétend tester le hors-ligne devra passer par `E2E_BASE_URL` sur un build de production, sinon il testera un SW en `NetworkOnly` et validera une illusion.

### 14. Contamination possible du critère anti-analytics de s01

Ajouter Serwist ajoute 31 paquets, dont `@swc/core` et `browserslist`. `serwist` expose `initializeGoogleAnalytics` / `offlineAnalyticsConfig` — **à ne jamais activer** : le PRD interdit tout traceur, et s01 a fait de l'absence d'analytics dans le build un critère vérifiable par recherche. `offlineAnalyticsConfig` est `undefined` par défaut, donc l'inaction suffit ; c'est l'activation « par curiosité » qui serait la faute.

### 15. Alignement de versions `serwist` ↔ `@serwist/turbopack`

L'exemple amont déclare `serwist: "preview"` (ligne 10.0.0-preview) avec `@serwist/turbopack: "latest"` (9.5.12), ce qui est un montage de monorepo, pas une recommandation. `@serwist/turbopack@9.5.12` dépend de `serwist@9.5.12` (version exacte). Installer `serwist@preview` à côté produirait deux copies et un `Serwist` incompatible avec le `defaultCache` importé de `@serwist/turbopack/worker`. **Épingler les deux sur `9.5.12`.**

## Open questions

1. **`mobile-web-app-capable` suffit-il sur l'iPhone cible ?** Next 16 n'émet plus `apple-mobile-web-app-capable` (vérifié dans `metadata.js`). La recherche web indique que depuis iOS 16.4 le mode standalone est piloté par `display: standalone` du manifest et que le tag legacy reste supporté — mais **je n'ai pas pu vérifier que Safari honore `mobile-web-app-capable`**, ni sur quelle version d'iOS tourne l'appareil de test. Si l'installation ne donne pas le standalone, le correctif est `metadata.other: { "apple-mobile-web-app-capable": "yes" }`. À constater sur l'appareil.
2. **Les service workers en module ES sont-ils supportés par l'iOS de test ?** `SerwistProvider` enregistre en `type: "module"` et esbuild produit de l'ESM. Repli identifié (`format: "iife"` + `type: "classic"`), non testé.
3. **L'en-tête `Service-Worker-Allowed: "/"` survit-il au prérendu statique de Vercel ?** Le handler le pose, mais la route est `force-static` : la réponse est prérendue au build. Si Vercel ne conserve pas les en-têtes personnalisés d'un route handler prérendu, le scope `/` est refusé. Une règle `headers()` dans `next.config.ts` sur `/serwist/:path*` est le filet ; reste à savoir s'il est nécessaire ou redondant.
4. **Comportement d'une preview Vercel protégée vis-à-vis du SW installé.** Le manifest est géré (`crossOrigin="use-credentials"`). Mais : le cookie d'authentification Vercel est-il partagé entre Safari et l'app installée sur l'écran d'accueil sur l'iOS cible ? Si non, le critère 6 (« installer une preview et rejouer deux déploiements ») est irréalisable tel quel et il faudra soit désactiver la protection sur la preview, soit basculer le protocole sur une URL de production. **Question bloquante pour l'écriture du protocole de review.**
5. **Où passe exactement la frontière entre « données à cacher » et « données à ne jamais cacher » ?** L'arbitrage dépend de la forme finale de s06 (silhouette rendue en Server Component ? données chargées par `fetch` client ?), qui n'est pas écrite. Sans elle, on ne peut pas décider si le « dernier état connu » se conserve via le cache HTML/RSC ou via un stockage applicatif distinct. À reprendre au `/ks-plan`, après s06.
6. **Quelle valeur pour `theme_color` / `background_color` ?** Design system gap n°3, non tranché. Les tokens sont en OKLCH et le manifest exige un littéral. La valeur doit être décidée avec l'utilisateur et inscrite dans `docs/design-system.md` avant l'exécution.
7. **Quelles tailles d'icônes et quel masque iOS ?** Le critère dit « icônes aux tailles requises » sans les énumérer. L'exemple amont fournit 192×192 (`purpose: "maskable"`), 512×512 et un `apple-touch-icon` 180×180. Aucune icône source n'existe dans le dépôt ; aucun outil de génération n'est installé. À trancher au design system, pas dans le code.
8. **Le refus de saisie hors ligne se décide-t-il côté client ou côté serveur ?** `navigator.onLine` est un signal notoirement optimiste (il ne dit que « une interface réseau est active »). Le critère demande un refus explicite ; il n'exige pas où il se prend. Comment ce refus s'articule avec le formulaire de s03/s05 (bouton désactivé ? soumission tentée puis toast d'échec ?) n'est arbitré nulle part et touche au budget des 20 secondes.
9. **Le manifest doit-il porter `start_url` protégé ?** `start_url: "/"` renvoie sur la route d'accueil authentifiée. Un lancement à froid sans session redirigera vers l'écran de connexion — comportement acceptable, mais l'interaction avec le cache HTML et le repli `~offline` n'est pas évidente et n'a pas été vérifiée.
10. **Faut-il un `id` dans le manifest ?** Le type l'autorise. En son absence, l'identité de l'app installée est dérivée de `start_url`, ce qui peut provoquer une seconde installation si `start_url` change. Non vérifié sur iOS.

## Blockers

Aucun credential n'est disponible dans cet environnement : pas de `DATABASE_URL`, pas de CLI Neon, pas de CLI Vercel, pas de projet Vercel joignable, pas d'appareil iOS. Conséquences concrètes :

- **Le critère 6 (deux déploiements de preview + lancement à froid) ne peut pas être exécuté ni automatisé ici.** Il exige une intervention humaine sur un iPhone réel et un projet Vercel configuré. Le plan doit le traiter comme une procédure manuelle documentée, et la review comme une preuve écrite (identifiants de déploiement).
- Les critères 1 et 2 (manifest valide, standalone sur iOS) ne sont vérifiables qu'à moitié sans appareil : la validité du manifest et la présence des balises sont vérifiables sur un build local ; l'installation et le mode standalone ne le sont pas.
- Le comportement du service worker sur une preview Vercel protégée (question ouverte n°4) ne peut pas être levé sans accès au projet Vercel.
